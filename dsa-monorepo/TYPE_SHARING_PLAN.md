# Type Sharing Implementation Plan

## Executive Summary

This document outlines the implementation plan for sharing TypeScript types between the Angular frontend and Next.js backend in the DSA Cockpit monorepo. The goal is to achieve type safety across the entire stack by creating a single source of truth for data structures.

## Current State

- **Backend**: Next.js with Prisma ORM generating types for `dsa_starter_character` (snake_case, database-centric)
- **Frontend**: Angular with `Hero` class (460 lines, tightly coupled to services, camelCase)
- **Issue**: Duplicate type definitions, no shared contract between frontend and backend

## Recommended Architecture: 4-Layer Type System

```
Layer 1: Database Types (Prisma-generated) → backend only
         ↓
Layer 2: Shared Base Types → packages/shared-types
         ↓
Layer 3: API DTOs (Data Transfer Objects) → packages/shared-types
         ↓
Layer 4: Domain Models (with business logic) → app-specific
```

### Layer Breakdown

**Layer 1: Database Types** (Backend Only)
- Location: `apps/backend/src/generated/prisma/`
- Source: Auto-generated by Prisma
- Format: snake_case (e.g., `dsa_starter_character`)
- Usage: Internal to backend only

**Layer 2: Shared Base Types**
- Location: `packages/shared-types/src/models/`
- Source: Generated from Prisma types via script
- Format: camelCase TypeScript interfaces
- Usage: Shared between frontend and backend
- Example: `Character`, `Skill`, `Spell`

**Layer 3: API DTOs**
- Location: `packages/shared-types/src/dtos/`
- Source: Manually created
- Purpose: API request/response contracts
- Example: `CharacterDetailDto`, `CreateCharacterDto`, `CharacterListDto`

**Layer 4: Domain Models**
- Location: App-specific (`apps/frontend/src/app/domain/`, `apps/backend/src/domain/`)
- Source: Classes with business logic
- Purpose: App-specific functionality
- Example: Frontend `Hero` interface extending `CharacterDetailDto`, Calculator services

## Implementation Phases

### Phase 1: Foundation (Week 1)
1. Create Prisma-to-TypeScript generator script
2. Generate base model types (Layer 2)
3. Define API DTOs (Layer 3)
4. Set up build pipeline

### Phase 2: Backend Integration (Week 2)
1. Create mapper functions (Prisma → DTO)
2. Update API routes to return DTOs
3. Update backend tests
4. Verify type safety

### Phase 3: Frontend Migration Part 1 (Week 3)
1. Extract business logic from Hero class to services
2. Create Hero mapper (DTO → Hero)
3. Update HeroService to consume DTOs
4. Update high-priority components

### Phase 4: Frontend Migration Part 2 & Cleanup (Week 4)
1. Update remaining components
2. Remove old Hero class
3. Documentation
4. Final testing

## Key Benefits

1. **Type Safety**: Compile-time errors when API contracts change
2. **Single Source of Truth**: Database schema drives all type definitions
3. **Reduced Duplication**: Same types used across frontend and backend
4. **Better Refactoring**: Safe, automated refactoring across the stack
5. **Self-Documenting**: Types serve as API documentation
6. **Framework Independence**: Shared types are framework-agnostic

## Example: Before vs After

### Before
```typescript
// Frontend: Hero class (460 lines, tightly coupled)
export class Hero {
  id: number;
  life: number;
  life_lost: number;  // snake_case from backend

  constructor(
    private skillService: SkillService,
    private spellService: SpellService
  ) {}

  get currentLife(): number {
    return this.life - this.life_lost;
  }

  setData(dataObject: Object): Promise<Hero> {
    // Manual mapping of 100+ fields
  }
}

// Backend: Returns raw Prisma types
return NextResponse.json({ character });  // snake_case
```

### After
```typescript
// Shared Types (packages/shared-types)
export interface CharacterDetailDto {
  id: number;
  life: number;
  lifeLost: number;  // camelCase
  heroType: HeroTypeDto;
  race: RaceDto;
  skills: ActualSkillDto[];
}

// Backend: Returns standardized DTOs
import { CharacterDetailDto } from '@dsa-monorepo/shared-types';
const dto: CharacterDetailDto = mapCharacterToDetailDto(character);
return NextResponse.json({ character: dto });

// Frontend: Hero extends DTO
import { CharacterDetailDto } from '@dsa-monorepo/shared-types';

export interface Hero extends CharacterDetailDto {
  // Computed properties only
  currentLife: number;
  armorValue: number;
}

// Frontend: Clean mapper service
export class HeroMapper {
  toHero(dto: CharacterDetailDto): Hero {
    return {
      ...dto,
      currentLife: this.calculator.calculateCurrentLife(dto),
      armorValue: this.calculator.calculateArmorValue(dto),
    };
  }
}
```

## Critical Success Factors

1. **Avoid Circular Dependencies**: shared-types must not import from apps
2. **Use Mappers**: Backend maps Prisma → DTO, Frontend maps DTO → Domain Model
3. **Type Generation**: Automate type generation from Prisma schema
4. **Gradual Migration**: Migrate one entity at a time, starting with Character
5. **Testing**: Comprehensive tests at each layer

## Migration Strategy for Hero Class

The current Hero class mixes concerns:
- Data storage (properties)
- Business logic (methods)
- Service dependencies (injected services)

**New approach**:
1. **Hero Interface**: Extends `CharacterDetailDto` with computed properties
2. **HeroCalculatorService**: Pure business logic (no dependencies)
3. **HeroMapper**: Transforms DTOs to Heroes
4. **HeroService**: Fetches data and uses mapper

This achieves:
- Separation of concerns
- Testability
- Type safety
- Reusability

## Potential Pitfalls & Mitigations

| Pitfall | Mitigation |
|---------|------------|
| Circular dependencies | Use generation scripts, not direct imports |
| snake_case vs camelCase | Mapper functions in backend handle conversion |
| Tight coupling to DB | DTOs abstract database schema |
| Breaking changes | Version DTOs (V1, V2), use deprecation warnings |
| Build order issues | Configure Nx dependency graph correctly |
